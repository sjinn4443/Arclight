## Summary

The central highest-urgency calculation is internally consistent. The main weaknesses are assessment completeness, recorded-versus-default context, image validation and modal behaviour. Clinical routing limitations must be resolved deliberately rather than replacing the teaching score with a new unapproved algorithm.

## Confirmed defects and presentation issues

1. **P1 — Incomplete rash assessment can look reassuring.** Selecting only Itch = Mild or none produces Routine (weeks). Duration, pattern and colour remain unselected and red flags remain Not checked. The report nevertheless exports that urgency. Reproduced in the browser. `script.js:1205–1220` treats any non-empty select, including value `0`, as sufficient assessment; `1164–1172` then displays the routine fallback. Keep available information usable but do not present a reassuring completed triage while danger signs are unchecked. Known urgent findings must continue to override incompleteness.

2. **P2 — Undecodable photo files count as attached.** A file called broken.png with image/png MIME type and invalid image contents is accepted: Photos 1/3, Close-up: attached in the report, naturalWidth = 0 and no upload error. `script.js:652–686` marks completion before decoding; `photo-file-store.js:33–40` checks only MIME and size. Decode before replacing the previous valid file or reporting readiness. Include zero-byte, corrupt, very large-dimension and replacement-failure cases.

3. **P2 — Storage denial interrupts initialisation.** The localStorage getter throws before the try in loadJsonStorage. A simulated SecurityError reproduces an uncaught error. `script.js:1391–1410`, called during initMcqUi, prevents the rest of the initialisation sequence from completing. Guard the capability probe as well as getItem/setItem and retain in-memory practice.

4. **P2 — Modal keyboard isolation and report focus return are incomplete.** Tab from the open guide reaches capture controls, route controls and underlying assessment inputs. Escape from the report leaves focus on closeReportModal inside the now-hidden dialog. `script.js:1382–1389` does not restore focus and there is no modal focus containment. This also permits keyboard changes behind a report whose text is a snapshot. Guide and MCQ Escape return work in the tested paths; the report needs equivalent treatment.

5. **P2 — Report context mixes defaults and recorded findings.** Untouched reports state Location: Head/Face and Skin context: Light. These are initial UI defaults, not affirmative patient entries. The expected-photo paragraph also changes simply by navigating from Lesion to Rash while Route used remains not selected (`script.js:849–857`, `973–1050`). Distinguish default/teaching context from patient-recorded context and derive report requirements from the recorded route. Do not require every field before producing a useful draft.

6. **P2 — Slow reference loading leaves the previous route's image visible.** With chaos_light.webp delayed, the Dermoscopy route still shows abcde-su-preview_light.webp. On ultimate failure the reference is hidden but the error alt text is hidden with it. `script.js:125–156` needs a visible loading/error state and a cleared or clearly pending old image. Request tokens already prevent late requests replacing newer successful images.

7. **P2 — Rash and Wood's tabs look disabled.** At 360 x 740 the Wood's tab is rendered as Woo… and both secondary tabs are exceptionally faint. The tabs are functional, not disabled. `styles.css:1246–1327` sets ellipsis, small targets and 0.56 opacity for the two inactive routes. Keep the established four-route layout but make every label readable and every available tab look available.

8. **P2 — Expanding information hides safety copy.** Opening More detail hides the initial purpose, emergency and privacy paragraphs. Opening sources does likewise. Confirmed emergencyVisible = false after expansion. `styles.css:3483–3492` explicitly hides these sections. Keep essential safety content available while folding genuinely secondary material. The closed guide itself fits: 660px tall with no internal scroll.

## Clinical and teaching decisions requiring review

9. **Operational melanoma/BCC limitations need an explicit safeguard.** All ABCDEFG combinations lead only to Photo + Review by design; this is not a validated melanoma referral rule. BCC-like features always lead to routine referral, with no exceptional concern about site or size input. These are not arithmetic bugs and should not be 'fixed' by mapping the teaching total to NICE. Provide an agreed way to represent independent clinical suspicion/override or make the limits unambiguous in the operational result. NICE NG12 distinguishes suspected melanoma, SCC and BCC with particular concern about delay.

10. **SCC trigger wording is broader than clinical suspicion.** The option 'keratinised, scaly or tender' immediately selects the suspected cancer pathway. Scale or tenderness alone is nonspecific. The grouped lesion context helps, but the label should express a concerning lesion/suspected SCC rather than suggesting any scaly or tender patch is SCC. Requires clinical wording approval, not an automatic new score.

11. **One Advanced MCQ understates its cited recommendation.** `allan-advanced-02`, `mcq-bank.js:248–253`, says NICE advises 'considering' referral at weighted 7-point score 3. NG12 1.7.1 says refer for a suspicious pigmented lesion meeting that threshold. Tighten the stem to that population and the answer to the actual recommendation. This does not authorise applying NICE thresholds to Allan's different ABCDEFG score.

12. **Emergency recognition is more complete in hidden detail than in the choice itself.** The emergency dropdown omits an unwell patient with a non-blanching rash; that example appears only in its disclosure. Make that route discoverable without relying on the user expanding help. Preserve agreed local timing and clinical judgement. The same-day MCQ involving pain, blistering or systemic illness also benefits from a clear distinction from emergency-level mucosal disease or systemic compromise.

## Photos, reporting and privacy

- User photographs remain File objects and object URLs in the current page. New assessment revokes active URLs, clears previews, input values and clinical selections. No patient-photo upload endpoint was found.
- Report rendering uses text nodes rather than inserting user text as HTML. The share path uses the original file bytes with generic output filenames and reports note-only fallback. Native OS share delivery and real camera permissions were not exercised; no external patient-data transfer was performed.
- Renaming does not strip EXIF/GPS or other metadata. This is a privacy limitation to disclose or address under the receiving service's policy, not evidence that files have already leaked.
- A report can be generated without photos. This is useful and should not be blocked merely because a photo is missing. The wording should distinguish ready in app from actually attached to a copied note or external message.
- Default report text is lengthy, including the entire general logic note. Keep findings and action prominent; consider moving generic teaching logic out of the copied clinical note after agreement.
